# Cilo 0.2 compression refinement — 2026-10-23

The six-build sample reaches **80.36% savings**, mainly by storing unchanged
content once. This is not an 80% improvement from the new compressor: Cilo 0.1
already saved 80.34% on the same sample. A single build's selected assets save
only **7.44%**. No complete game build was compressed or measured.

The strongest measured improvements are faster fast/balanced ingestion of
repeated builds and a **4.33% smaller DLL archive**. Max mode spends more CPU
trialing filters for relatively small overall gains; some formats regress.
Balanced remains the recommended starting point. The format modules preserve
original encoded bytes, including signatures, authentication pages and media.

## Corpus and method

- Six distinct retail **odin** builds: 11521872, 11531527, 11744825, 11558592,
  11642448, 11810757. Eleven complete asset paths per build, 66 files totaling
  1,208,362,280 bytes (1,152.38 MiB). These are deliberately related builds and
  recurring paths, not a random or representative sample of an entire game.
- The original three-build subset is 576.10 MiB; the single-build subset is
  191.86 MiB. The first two builds have identical sampled files; eight of the
  eleven paths are unchanged across the original three. Extra builds were
  actually downloaded and verified, not generated by copying one build.
- Types: FF, FP, SAB, XPAK, Bink and DLSS DLL. A separately downloaded 289.04 MiB
  `modernwarfare.exe` is measured in the type table, not included in the six-build
  headline. No game executable or DLL was executed. Payloads are not distributed.
- Linux 6.18.55, AMD EPYC 9V74 host, five visible logical CPUs, four compression
  workers, Rust 1.90.0 release builds. Warm source cache on a shared cloud host.
  Default 0.1 block size 32 MiB versus 0.2's 64 MiB; default chunk target 256 KiB.
- Three runs per version/profile/dataset, alternating version order. Tables show
  median elapsed throughput, including hashes, I/O and filesystem sync. Every
  restore independently matched the input SHA-256 inventory; that extra hash
  comparison is excluded from timings. Network time is excluded. MiB = 2^20 bytes.
  These are logical input-byte speeds, including duplicate data.
- Timing binaries and all individual runs are recorded in
  [refinement-linux.json](refinement-linux.json). These measurements precede the
  downloader/browser integration refactor. The final release integration check
  reproduces the exact six-build max archive size and verifies cross-platform
  SHA-256 restoration; its binary hashes are in
  [refinement-final-validation.json](refinement-final-validation.json). No claim
  is made that Wine results are native Windows performance measurements.

On six builds, balanced packs about **12.7% faster** with a **0.096% smaller
archive**, while fast packs about **74% faster** but produces a **0.065% larger
archive**. Max's archive is **0.116% smaller**, but packing is about **15% slower**
and restoration about **3.3% slower**. Single-build max is 2,124 bytes larger
than 0.1. The new layout is not universally better; `--generic` disables format
parsers/filters for comparisons, while retaining the new pipeline and defaults.

## Per-type exploratory measurements

These are **one run per version**, max profile, single-build files grouped by
extension. They are useful for ratio comparisons, not precise speed rankings.
The small group archives are not additive: solid grouping differs from packing
the complete sample. Full results are in
[refinement-types-linux.json](refinement-types-linux.json).

| .exe | 289.04 | 217.544 | 217.523 | 24.74% | 17.0 / 12.4 | 682.1 / 516.1 |

The DLSS DLL benefits from branch normalization and byte-plane shuffling.
The main EXE has large sections that barely compress; its improvement is tiny.
FF/FP, audio banks and Bink are already compressed internally. Container-aware
chunking aims to recover shared assets when containers change or reorder; it
can cost a little ratio on one unchanged standalone file. A synthetic reordered
650-object sound-bank test demonstrates the boundary-based deduplication case;
it is not included in any real-game headline result.

The implementation compares actual plain, filtered and raw block sizes before
choosing a codec. That prevents an individual filter from expanding a block,
but does not guarantee that a different chunk layout or solid-block grouping
beats the previous version. Larger block sizes, smaller chunk sizes, mixed
filtered blocks, dictionary references and PE section strategies were tried;
see [format decisions](../docs/GAME_FORMATS.md).

## Download-to-archive validation

A fresh live CDN extraction of `campaignmenu.bik`, `nvngx_dlss.dll`, and
`common.ff` from build 11558592 streamed directly into a 24,477,656-byte archive
from 34,937,404 decoded bytes (29.94% saved). The native verifier passed, and
reading each file back independently matched SHA-256 from the earlier downloads.
Only the completed archive remained in the output directory. This deliberately
small mixed subset is a functional test, not a whole-build ratio estimate.
Local HTTP tests also cover encoded mirroring, corrupted payload rejection,
short writes, cancellation, and refusing existing archives/symlinks.

## Reproduce

[refinement-corpus.json](refinement-corpus.json) records all 67 source files,
build/config identities, sizes, SHA-256 and CASC object references. Use the
Python downloader with those exact configurations and paths. Keep each build's
files beneath a distinct build directory. Download all files before timing.
Obtain/build the previous version separately; never execute the game EXE.

Create a JSON dataset file with entries such as:

```json
[{"name":"six-builds","root":"/data/six-builds"}]
```

Then, from the repository root:

```sh
cargo build --release --locked
node tools/benchmark-refinement.mjs datasets.json results.json /path/to/cilo-v0.1.0 3
```

For type trials, group complete files by extension and add `"profiles":["max"]`
to each dataset. Use one repetition for the same exploratory setup or more for
stronger timing estimates. The harness writes all runs and input SHA-256 lists,
checks every restore, and removes its temporary archives/restores in a `finally`
block. Machine, storage, source entropy and build overlap materially change
these results; no prediction of an 80% saving for a new build is justified.
